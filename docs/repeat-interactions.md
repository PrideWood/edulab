# 多次交互与身份管理

## 学生操作

1. 使用教师提供的原分组链接进入，首次未经验证仍需网站访问码。
2. 首次参与填写姓名，学号可留空；首尾空格自动清除。提交成功后弹窗提醒保存原有 P/T 编号，关闭后可在左下角参与者信息中查看、复制。
3. 已有编号使用“继续之前的实验”，填写编号及当前姓名或学号。姓名和学号任一准确匹配即可；服务端限定当前项目与原分组，不会新建被试、重新编号或重新随机分组。
4. 恢复后从侧栏选择旧会话，继续未完成交互。旧会话已结束时仅查看，不自动重新开始。
5. 下一次学习任务明确点击“开始新一次交互”，确认后新建独立会话，原编号、内部身份及智能体不变。旧会话结束并保留消息、完成时间和未发送草稿；新会话使用新的开始时间和当前项目任务/规则，重新计算本次次数与时长。

同一设备使用有效 HttpOnly 身份 Cookie 自动恢复，不以姓名查找或猜测身份。更换设备通过编号加身份信息恢复，原设备写入凭证失效。每个项目与分组入口 Cookie 独立。两名重名学生可获得不同编号，不会合并；非空学号同一项目唯一，不同项目可以再次使用相同姓名或学号。

本功能不配置课次、不判断日期间隔、不管理班级进度。独立会话 ID 与开始时间用于后续按时间分析。需要单次实验的项目可继续只使用首次会话；恢复、刷新、切换及兼容的同次交互内多对话不重置原限制。

## 教师操作

- 原分组链接可以用于同一被试的多次参与。“停止新报名”保留既有学生恢复及新交互能力；删除链接会撤销该入口的学生访问。研究条件或智能体本体改变应使用新项目/配置，API Key 续期仍在原行更新。
- 第一轮报名沿用入口既有的任务快照。已有会话恢复沿用其原快照。明确开始新交互时读取当前已保存的项目任务、规则、存储与历史设置，原 AI 提供商、API 地址、Bot ID、分组和分配不变。因此后续任务应先在后台保存，再让学生点击新交互。
- 参与者目录 → “编辑信息”：姓名必填、允许重名，学号可留空。编号、参与者 UUID、分组、全部会话和消息不变。填写已被其他学生使用的非空学号会被拒绝；不同窗口同时编辑按身份版本拒绝陈旧覆盖。修改后学生使用当前姓名或学号及原编号登录。
- “编辑信息”中的修改记录展示修改前后内容、管理员和时间。审计正文加密保存；学生自行纠正已有信息也记录为学生本人。仅已认证管理员可读取解密日志。
- “查看交互”按开始时间列出所有 Session，可查看严格有序的原始消息、未发送草稿和历史加载信息。交互 ZIP 每个 Session 独立 JSON，保留项目、参与者内部 ID/编号、组别、会话 ID、时间、原消息、交互关联及历史来源。身份 CSV 仍与研究聊天数据分开导出。

## 历史加载规则

默认开启，项目各组共用同一套规则和预算。只读取数据库中同一参与者 UUID、同一项目、同一原入口和智能体的既往消息，排除当前新会话。按请求时间、会话开始时间、轮次及消息序号排序，保存读取截止时间。

Coze 与 Dify 均将完整背景作为新会话首条普通用户请求中的引用 JSON：

- `history` 包含历史会话/消息 ID、角色、正文、序号及时间；仅引用背景，不导入新会话的消息表。
- `currentTask` 为当前会话快照中的可见任务，`question` 为学生本次真正输入。提示明确要求历史指令不能覆盖当前智能体系统规则和本次任务，不设置或替换远端系统提示词。
- Coze 使用单条 `additional_messages` 用户消息，Dify 使用 `query`，不依赖 Dify 必填自定义 inputs。后续沿用本次提供商 Conversation ID，不重复注入相同背景。
- 数据库及学生页面仅保存、显示真正的新问题与新回复；断线恢复从提供商 query 读取原问题时，只对服务端标记注入历史的请求解包。

每次会话的 `metadata.history_memory` 保存策略 `full_or_block`、状态、截止时间、来源 Session/Message ID、SHA-256 指纹、消息数量、预算和估算方式；首次请求另存实际注入决定。后台查询和交互 ZIP 可追溯这些信息，但不会复制历史正文进新 Session。

输入预算默认 6000、后台范围 512–100000，按 UTF-8 字节数除以 2 估算 Token。估算不是提供商真实 tokenizer 的计费值；应按实际模型窗口设置，并给远端系统提示词、工具/知识库背景及回复留余量。关闭数据库正文保存时无法承诺完整跨会话历史。

应用采用完整继承或明确阻止，不自动总结或截断：

- 超预算：记录 `too_long`，首条消息不创建请求、不写入新用户消息、不调用 AI，提示教师处理。首条真实问题加入背景后再次检查总预算。
- 已完成请求缺失数据库用户/AI 消息，或有结果未核实的 `uncertain` 请求：记录 `incomplete` 并阻止发送。
- 来源在读取后发生变化：指纹校验失败，阻止发送并提示核验。
- 教师在后台明确关闭继承：记录 `disabled`，既往原始记录保留；新交互仍使用当前可见任务。

历史设置随新会话快照固定。教师调整预算或关闭继承后，学生明确开始新的交互应用更新设置；既有会话不会被暗中改写。此时被阻止的空会话也保留，方便审计。

远端 Coze/Dify 应用自己的上下文窗口、记忆设置或自动裁剪策略由平台管理，EduLab 不能通过通用聊天 API 核实或关闭这些行为。本实现保证发送的数据库历史完整且不静默删减，不能保证模型永远准确记住每条内容。正式研究前应检查原智能体的模型窗口和上下文设置，并用后台连通测试及研究预试核验实际行为。

## 并发、错误与兼容

- 沿用原 P/T 分配算法、按项目/前缀的事务 advisory lock 和“项目 + 编号”数据库唯一约束，组别不各自编号。
- 首次报名使用浏览器保存的随机报名请求 ID、服务端报名锁和唯一索引；网络重试只返回同一身份及 Session。请求复用时还验证原姓名、学号和入口；无法证明是同一次报名时拒绝复用。
- 非空学号检查在项目身份事务锁内解密既有身份表完成，兼容旧加密记录，不增添明文学号或第二套学生账号。名字从不作为合并键。
- 新交互使用随机请求 ID、参与者行锁、预期原会话和唯一索引。同一请求重试复用创建结果；来自同一旧会话的两个不同并发请求只能一个成功，另一个提示进入最新交互。学生侧在请求结果不明确时保留重试 ID。
- 原组有 AI 回复正在生成时拒绝创建下一次交互，先恢复原请求；不会截断生成中的原始数据。
- 新会话创建、结束旧交互、恢复指针及历史加载信息在同一事务内提交；数据库失败整体回滚。身份纠正和加密修改日志同样原子提交，不会在失败时显示保存成功。
- 沿用消息请求幂等、服务端消息序号、草稿版本、浏览器 outbox 和提供商检查点；刷新及恢复 GET 不创建新会话。

旧会话不需要补写历史消息或重置数据。没有新交互 metadata 的旧对话保留原累计限制与提供商上下文。原来只填学号/只填姓名的记录可以恢复；缺少身份、绑定或必要上下文的记录明确提示教师核验，不猜测分组。旧数据库若已有重复学号，不删除或合并历史记录；再次修改为冲突非空学号时要求管理员处理。
